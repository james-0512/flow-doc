# 已知限制

> 新目標的起點範本。`<N>` 的地方填該專案 `flow-doc entries` / `trace` 實際跑出來的數字，
> 沒發生的段落整段刪掉（例如專案沒用 SignalR 就不要留著）。
> 這份檔案會被 `pack` 注入封包總覽、被 `site` 產成「已知限制」頁。

這份手冊由靜態分析產生。以下是**分析器看不到、或刻意不追**的東西。
讀手冊時請把這份清單當成「手冊沒說的部分」的完整列表——不在這裡的遺漏才是 bug。

## 一、刻意未實作（決策，非缺陷）

### reactive 連動（`watch` / `watchEffect`）未追蹤

專案有 `<N>` 處。`watch(() => store.x, …)` 沒有語法上的 join key，要接就得做
「誰寫了 `store.x`」的 data-flow 分析——成本高一個量級，且誤判會產生假步驟。
**假步驟比缺步驟更傷手冊的可信度**，這是整份設計反覆採用的取捨。

### `defineExpose` + template ref 呼叫未追蹤

專案有 `<N>` 處。父元件透過 `ref` 直接呼叫子元件方法，需要 template ref 的型別解析。

### 伺服器主動推送未追蹤（若專案有 SignalR / WebSocket）

`<N>` 處。除了事件名常是變數（沒有 join key），語意上它也不是既有鏈的延伸而是
**新的流程起點**——handler 被觸發時沒有使用者動作在前面，要正確表達需要新的 entry 類型。

影響：涉及即時通知的流程，手冊只會描述使用者主動觸發的那一半。

## 二、覆蓋率缺口（缺陷，待補）

### 頁面載入流程偏少

`<N>` 條流程中有 `<N>` 條由頁面載入觸發。除了 `onMounted` 之外的初始化寫法
（`watch(…, { immediate: true })`、自訂 composable）目前不被視為流程起點。

### 動態元件上的事件接不起來

`<component :is="…" @evt="handler">` 的標籤無法靜態解析成檔案，子元件的 `emit`
找不到這個 listener。全 repo `<N>` 處 emit 接不到。屬靜態分析的固有極限。

### 賦值型副作用不列入副作用清單

分析器追的是**函式呼叫**，不追賦值：攔截器注入的標頭、直接寫 store state、
本地狀態切換都不會出現在副作用清單。緩解方式是封包附上鏈上每個函式的完整原始碼，
敘述可以據此寫準。

## 三、判準排除的東西

一條 entry 要成為「業務流程」，判準是**鏈中至少跨越一次 HTTP 邊界**（不論讀寫），
再依此分成「寫入型」與「查詢型」。被排除的是完全沒碰後端的 `<N>` 條鏈：
開 modal、切 tab、toggle 顯示、本地表單欄位互動。

若某個操作你認為是業務流程卻不在手冊裡，最可能的原因是它沒有任何後端互動。

## 四、鏈的展開上限

這節是分析器的固定行為，各專案通用，數值可由 `--max-depth` 等參數調整。

- **深度上限 8 層**、**單鏈節點預算 250**。到達上限的節點在封包裡標為
  「達深度上限／達節點預算」，不會靜默截斷。
- **一個 emit 最多展開 5 個父層 listener**，超出的數量會標示「另有 N 個父層也監聽此事件」。
- **同一個函式在同一條鏈中只完整展開一次**，後續以「同前」參照取代。
